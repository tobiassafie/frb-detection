## E: II diagnosis (done, no synthesis needed)

**No free-text "II violation" message exists anywhere in the logs** (`solution1.log`,
`synthesis.log`, `logs/hls_run_tcl.log`, all `.autopilot/db/*.log` files — searched all of
them). Vitis records the shortfall as a schedule-table entry instead, found in
`frb_classifier_prj/solution1/.autopilot/db/conv_2d_cl_..._config2_s.verbose.sched.rpt`:

```
Loop Name                          Latency  Iteration  II achieved  II target  Trip Count  Pipelined
ReadInputHeight_ReadInputWidth     12289    5          3            1          4096        yes
```

That table row **is** the verbatim record: hls4ml's codegen requests `II=1` (visible in the
same report as `specpipeline_ln28 ... i32 1`, i.e. a `#pragma HLS PIPELINE II=1`), and Vitis's
scheduler could only deliver `II=3`.

**Why (my reading of the schedule, not a quoted Vitis explanation):** the same report's FSM
schedule shows that each pixel read (state 2) fans out into a call to
`compute_output_buffer_2d` — the function that shifts the pixel into the line buffer and
evaluates the 3×3 MAC (this repo's `shift_line_buffer_..._config2_s` module, an
`ap_shift_reg`-based line buffer). That call appears as a 4-cycle-latency, `[k/4]`-tagged
"Generic Core" invocation spanning states 2→5, and a new one can only be issued every 3
cycles — consistent with the shift-register line buffer's limited read/write ports per cycle.

### Candidates investigated for a config-only fix

I checked which levers hls4ml's Vitis backend actually wires up (grepped the installed
hls4ml 1.3.0 source directly, not just the YAML schema) before proposing anything:

- **`ConvImplementation: Encoded`** — rejected. The Vitis-backend io_stream Conv2D template
  (`hls4ml/templates/vitis/nnet_utils/nnet_conv2d_stream.h`) has
  `assert(CONFIG_T::implementation == conv_implementation::linebuffer && ...)` — `Encoded`
  would fail to compile for io_stream Conv2D on this backend. Not usable here.
- **`ParallelizationFactor`** — real and wired (`hls4ml/backends/vivado/vivado_backend.py:init_conv2d`,
  inherited by the Vitis backend), despite the key not appearing anywhere else in the codebase
  under a quick literal search — it only shows up in that one `init_conv2d` function, is easy to
  miss, and I initially got a false negative before checking directly. It controls how many
  output-pixel partitions the io_stream conv is split into (`n_partitions = out_h*out_w // PF`).
  Valid values are constrained to divisors found by `get_valid_conv_partition_splits()`: for
  conv2d's 62×62 output, valid PFs are `{1,2,4,31,62,124,961,1922,3844}`; for conv2d_1's 29×29
  output, `{1,29,841}`.
- **`ReuseFactor`** — real and wired throughout (dense/resource binding). Currently 1 everywhere
  (asking for max parallelism); explicitly setting it to 3 on the conv layers matches what
  Vitis already delivers rather than asking for something it can't give.

### Two candidate projects generated (config-only diffs, no hand-edited firmware)

Both were generated by loading `classifier/frb_classifier_pooled.h5`'s weights into the exact
architecture from `context/frb_pooled_synthesis(1)(2).ipynb`'s `create_simple_cnn` (Conv2D→Pool→
Dropout→Conv2D→Pool→Flatten→Dense, matches the original bit-for-bit — see
`scripts/generate_E_variants.py`), then calling hls4ml's `convert_from_keras_model(...).write()`
— **`.write()` only, never `.build()`**, so no synthesis was invoked locally. Synthesis is left
to `run_synthesis.sh` → `vitis-run --mode hls --tcl run_synthesis.tcl`, the same invocation
style as the original `frb_pooled_hls/frb_pooled_hls/run_synthesis.sh`. Same part
(`xcvu9p-flga2104-2L-e`), same 200 MHz clock (`clock_period=5`), same `ap_fixed<16,6>`,
same `io_stream`, same `config_compile -pipeline_loops 64`.

| Variant | Directory | Change from baseline |
|---|---|---|
| **E1** | `E_fixes/E1_parallelization_factor/` | `ParallelizationFactor: 4` on `conv2d`, `29` on `conv2d_1` (nothing else changed) |
| **E2** | `E_fixes/E2_reusefactor3/` | `ReuseFactor: 3` on `conv2d` and `conv2d_1` (nothing else changed) |

**Caveat on version fidelity:** the original `frb_pooled_hls/frb_pooled_hls/hls4ml_config.yml`
doesn't list `ParallelizationFactor` or `ConvImplementation` for conv layers at all (implying an
older/different hls4ml version generated it, one where those keys either didn't exist yet or
weren't auto-populated), whereas the installed hls4ml (1.3.0) lists both explicitly with the
same default values (`ParallelizationFactor: 1`, `ConvImplementation: LineBuffer`). Functionally
this should be a no-op difference at the baseline, but it means E1/E2's generated firmware
won't be byte-identical to the original project's codegen even before my override is applied —
flagging this rather than assuming it's inconsequential.

**Expected outcome, stated plainly so it's falsifiable:** I expect E2 (RF=3) to leave latency
and II essentially unchanged (it's just telling Vitis to stop trying for II=1) but possibly
reduce DSP/LUT slightly by removing wasted over-provisioning for an unreachable II=1. I expect
E1 (PF=4/29) to be the one that could actually change the achieved II or total conv2d latency,
by restructuring how many output pixels are computed per line-buffer pass — but I have not run
it, so this is a prediction to check against the real report, not a claim.

## F: co-simulation setup

`frb_pooled_hls/frb_pooled_hls/tb_data/` was already empty in the original project — no
csim or cosim has ever been run on it, so there's nothing to compare against yet.

- **`F_cosim/frb_pooled_hls_copy/`** — a full copy of the unmodified `frb_pooled_hls/frb_pooled_hls`
  project (including its already-completed `frb_classifier_prj/solution1` synthesis database),
  with 8 real test vectors dropped into `tb_data/` (see below). `frb_pooled_hls/` itself is
  untouched — verified its `tb_data/` is still empty after this copy was made.
- **Test vectors** (`scripts/generate_F_tb_data.py`): 8 samples from
  `classifier/fetch/test_data.hdf5` (4 labeled RFI, 4 labeled FRB, chunk-aligned reads for
  speed) — `data_dm_time`, resized 256×256→64×64 with `tf.image.resize`, exactly matching
  `classifier/frb_classifier_pooled.ipynb`'s preprocessing (see `00b_fetch_dataset_provenance.md`
  and `02_final.md` for why `data_dm_time`, not `data_freq_time`). Reference softmax outputs
  come from the same rebuilt-and-reweighted float Keras model, for the testbench's own
  built-in comparison printout — not an accuracy claim, just a golden reference for the RTL
  simulator to check against.
- **`run_cosim.tcl`/`run_cosim.sh`**: opens the existing `solution1` (reusing its cached
  C-synthesis rather than re-running it), runs `csim_design` then
  `cosim_design -trace_level all -rtl verilog`. If Vitis complains it can't find valid RTL to
  simulate, uncomment the `csynth_design` line in `run_cosim.tcl` first.
